You are a database correctness engineer. Below is a FastAPI endpoint and its PostgreSQL schema. Many requests may hit it at the same time. Propose business invariants that must ALWAYS hold once any set of concurrent requests has finished, so that a violated invariant reveals a concurrency bug (race condition, lost update, double spend, duplicate row).

TABLES AVAILABLE when an invariant is checked. Use ONLY these tables with exactly these columns:
- the app's own table(s), shown in the schema below, holding the FINAL state after the run
- snap_<table> for every app table: an exact copy of that table taken BEFORE the run (same columns). Use it as the "initial state".
- ops_log(op_id int, endpoint text, params jsonb, status int, amount int, qty int, user_id int, code text): one row per request sent during the run. status is the HTTP status: 2xx (200, 201, 204...) = success, anything else = rejected or failed; look at the code to see which success status the endpoint returns (for example 201 for a created resource) and use that one. params holds ALL the request's values (path values, query values and the top-level fields of a JSON body) as JSON (read a value with (params->>'name')::int). amount/qty/user_id/code are convenience copies when the request had a parameter with that name; otherwise NULL.

OUTPUT CONTRACT for each invariant: a single PostgreSQL SELECT statement that returns ZERO ROWS when the invariant holds and AT LEAST ONE ROW when it is violated. Put the violation test in WHERE or HAVING. Never write a query that always returns a row (for example SELECT COUNT(*) ... or SELECT a - b ...). Do not use placeholders such as %s. Do not assume how many requests were sent or what their parameters are.

GUIDANCE: good invariants relate three things: the state before the run (snap_ tables), the successful operations in ops_log (status = the endpoint's success status), and the final state (conservation: nothing is created or lost), or they state that something must stay unique. A check on the final state alone can miss lost updates.

WORKED EXAMPLE (a different app, for format only). App: ticket shop with table tickets(event_id int, seats_left int) and endpoint POST /book(qty).
Conservation: SELECT 1 FROM snap_tickets s, tickets t WHERE s.seats_left <> t.seats_left + COALESCE((SELECT SUM((params->>'qty')::int) FROM ops_log WHERE endpoint = '/book' AND status = 200), 0)
